File Tracking Control

Git Ignore

Tell Git which files should never become part of your history — and understand exactly why that matters.

📁 Working Directory → Untracked File → git add → Tracked File → git commit → Repository

Git Ignore only influences files that have never been tracked. Once tracked, .gitignore has no effect.

Why Does .gitignore Exist?

🔐

Secret Files (.env)

API keys, database passwords, and tokens should never be committed to Git history.

📦

Downloaded Dependencies (node_modules/)

Hundreds of megabytes of packages that can be reinstalled with npm install.

🏗️

Build Artifacts (dist/, build/)

Generated output files — they change every build and bloat your history.

📋

Log Files (*.log)

Runtime logs are machine-generated noise that adds nothing to your project history.

💻

IDE Config (.vscode/, .idea/)

Personal editor preferences that vary per developer and should not be shared.

🗂️

OS Files (.DS_Store, Thumbs.db)

Invisible files created by macOS and Windows that have nothing to do with your code.

🧪

Test Coverage Reports

Generated test output — reproducible on any machine, no need to track it.

⚡

Cache Folders (.cache/, .next/)

Temporary performance artifacts that are rebuilt automatically.

Tracked vs Untracked — The Foundation

Git only knows about files you have explicitly introduced via git add. A file in your folder that has never been git added is Untracked — invisible to Git's tracking system.

📁 my-project/
├── 📄 app.js✅ Tracked
├── 📄 style.css✅ Tracked
├── 📄 README.md✅ Tracked
├── 📄 notes.txt⚪ Untracked
├── 📄 .env⚪ Untracked
└── 📁 node_modules/⚪ Untracked
Key insight: .gitignore rules only prevent Git from tracking Untracked files. If a file is already Tracked, adding it to .gitignore does nothing.
  • 📄 It is a plain text file named .gitignore
  • 📍 Placed in the root of your repository
  • 📝 Each line is a pattern telling Git what to ignore
  • 🚫 It does NOT delete files
  • 🙈 It does NOT hide files from your OS
  • ⚙️ It ONLY affects Git's file tracking decisions
.gitignore 
# Dependencies
node_modules/

# Environment secrets
.env
.env.local

# Build output
dist/
build/

# Logs
*.log

# OS files
.DS_Store
Thumbs.db

# Editor config
.vscode/
.idea/

Pattern Syntax — How Rules Work

Rule: password.txt

Ignores exactly one file with that exact name.

app.js
password.txt Ignored
style.css

Rule: *.log

* means "any filename". This ignores every file ending in .log regardless of name.

app.js
error.log Ignored
access.log Ignored
debug.log Ignored

Rule: node_modules/

The trailing / means "this is a folder". Every file inside it — no matter how deeply nested — is ignored.

src/
📁 node_modules/ Ignored Folder
react/
lodash/
* → matches any sequence of characters
example: *.log
✓ error.log ✓ app.log ✓ x.log ✗ app.js
? → matches exactly one character
example: file?.txt
✓ file1.txt ✓ fileA.txt ✗ file10.txt
[abc] → matches one character from the set
example: file[123].txt
✓ file1.txt ✓ file2.txt ✓ file3.txt ✗ file4.txt

Rules: *.md then !README.md

The ! prefix un-ignores a previously ignored file. Rules are processed top-to-bottom. The last matching rule wins.

README.md
matched *.md → ignored matched !README.md → un-ignored
✅ Tracked
Notes.md
matched *.md → ignored no exception
🚫 Ignored
Guide.md
matched *.md → ignored no exception
🚫 Ignored

⚠️ .gitignore Only Works For Untracked Files

Step 1 — Setup

# config.json gets committed
git add config.json
git commit -m "add config"
config.json ✅ Tracked

Step 2 — Added to .gitignore

# .gitignore
config.json
config.json ✅ Tracked Ignored?

Step 3 — The Answer

config.json ✅ Still Tracked
Git says: "I already know about config.json. It's in my tracking system. .gitignore cannot reach files I'm already tracking."

Why: Git's tracking state is stored in the index. Once a file is indexed, .gitignore patterns are never evaluated for it.

How to fix it:

git rm --cached config.json
# Now Git forgets it ever tracked this file
# .gitignore can now apply
git commit -m "stop tracking config.json"
config.json ✅ Ignored
The local file still exists on your disk — git rm --cached only removes it from Git's index, not from your file system.

🔴 Security Warning: The .env Trap

👨‍💻 1. Developer creates project — writes API keys and DB password into .env
😰 2. Accidentally runs git add .env then git commit
🌐 3. Pushes to GitHub — .env is now public in Git history
💡 4. Realizes the mistake — adds .env to .gitignore
❓ 5. "Is the secret safe now?"
❌ NO. The secret is NOT safe. Git history is permanent. Every previous commit still contains .env. Anyone with access to the repository can run: git log --all -- .env git show <commit-hash>:.env ...and retrieve the original secrets.

What you must do:

🔄
Rotate Immediately

Revoke and regenerate ALL exposed credentials right now

🗑️
Remove from index

git rm --cached .env + commit

📝
Add to .gitignore

Prevent future accidents

📚
Rewrite History (Adv)

git filter-branch or BFG Repo Cleaner

Key insight: git rm --cached removes the file from future commits — but it cannot erase it from past commits. The secret already exists in your commit history. Treat exposed credentials as permanently compromised.

Common Mistakes

❌ Myth: "I added .env to .gitignore — it's safe"
✅ Reality: Only safe if .env was never committed. Check your history.
❌ Myth: ".gitignore deletes the file"
✅ Reality: It only affects tracking. Your local file is untouched.
❌ Myth: "Adding a tracked file to .gitignore ignores it"
✅ Reality: No. Use git rm --cached first.
❌ Myth: "I can use .gitignore to hide files from collaborators"
✅ Reality: It only affects untracked files. Already-tracked files are still visible to everyone.
❌ Myth: "node_modules/ and dist/ don't need ignoring"
✅ Reality: Always ignore them — they create enormous repositories and break git clone.
❌ Myth: "I need to add .gitignore after finishing the project"
✅ Reality: Add it before your first commit. Retrofitting is much harder.

Exercise 1

.gitignore:
  *.md
  !README.md

Files in project:
  README.md
  Notes.md
  Guide.md

Predict: Which files does Git track?

Correct! *.md ignores all markdown files. !README.md creates an exception — only README.md survives as tracked.

Exercise 2

Steps:
  1. git add config.json
  2. git commit -m "add config"
  3. Add "config.json" to .gitignore

Predict: Will Git ignore config.json after step 3?

Correct! .gitignore only affects untracked files. config.json was committed — it's in Git's index. Use git rm --cached config.json to stop tracking it.

Exercise 3

.gitignore:
  node_modules/

Predict: What does Git ignore?

Correct! A trailing / in .gitignore means "this is a directory". Everything inside, at any depth of nesting, is ignored.

Exercise 4

Scenario:
  - Developer committed .env 3 months ago
  - Yesterday added .env to .gitignore
  - Ran git rm --cached .env + committed

Predict: Are the API keys safe from exposure?

Correct! git rm --cached removes the file from future commits only. The 3-month-old commit still contains the original .env. The keys must be rotated immediately.

Key Takeaways

🎯 .gitignore exists to keep repositories clean from noise, secrets, and generated files
🔒 Never commit .env — add it to .gitignore before your first git add
⚠️ .gitignore only works on untracked files — it cannot un-track already-committed files
🗂️ To stop tracking a committed file: git rm --cached <file> + commit
📜 Git history is permanent — git rm --cached does NOT erase past commits
✨ The ! prefix creates exceptions — !README.md overrides a *.md ignore rule
🔄 When in doubt, use gitignore.io to generate battle-tested templates

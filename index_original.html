Core Concepts

The essential vocabulary every developer needs to master Git.

📁

Working Directory

The folder on your computer where you write and edit code. Files here are either untracked or modified.

📋

Staging Area

Also called the "index". A preparation zone — files you've git added live here, waiting for the next commit.

💾

Local Repository

The .git hidden folder inside your project. It holds the complete history of every commit ever made.

☁️

Remote Repository

A hosted version of your project (GitHub, GitLab, Bitbucket). Shared with collaborators worldwide.

🌿

Branch

A parallel version of your codebase. main is the default. Create branches to work on features safely.

📸

Commit

A timestamped snapshot of staged changes. Commits form a permanent, immutable chain — the project timeline.

🔗

Merge

Combine changes from one branch into another. Git auto-merges when possible; conflicts require manual resolution.

🔄

Pull Request

A GitHub feature to propose merging your branch into the main codebase. Enables team code review and discussion.

Security & Authentication

Generate & Test GitHub SSH Keys

Securely connect your local machine to GitHub without typing your password every time.

Why SSH?

Why SSH Keys are Used

  • Problem with HTTPS: Requires a personal access token (or password) every time you push or pull.
  • Benefits of SSH: Uses cryptographic keys for secure, passwordless authentication.
Key Pair

SSH Key Pair

SSH uses two linked keys:

  • Private Key (id_rsa): Stays on your machine. NEVER share this.
  • Public Key (id_rsa.pub): Uploaded safely to GitHub.
Generate Key

Generate SSH Key

Run the following command in your terminal, replacing the email with your GitHub email:

ssh-keygen -t rsa -b 4096 -C "your_email@example.com"

Explanation:

  • ssh-keygen: The key-generation program.
  • -t rsa: Specifies the RSA algorithm.
  • -b 4096: Specifies a strong 4096-bit key size.
  • -C "email": Adds a label (comment) to identify the key.
Passphrase

Optional Passphrase

When prompted, you can enter an optional passphrase for extra security. If someone steals your laptop, they still need the passphrase to use the key.

Add to GitHub

Add Public Key to GitHub

  1. Copy the contents of ~/.ssh/id_rsa.pub
  2. Go to GitHub ➔ Settings
  3. Click SSH and GPG keys
  4. Click New SSH key and paste the contents.
Test Connection

Test Authentication

Verify that your key is correctly set up and recognized by GitHub.

ssh -T git@github.com

Expected Output:

bash — ssh-test
$ ssh -T git@github.com
Hi username! You've successfully authenticated, but GitHub does not provide shell access.

Pull Request Deep Dive

Master the core mechanism of GitHub collaboration, from your first PR to advanced code review workflows.

🤔

What is a Pull Request?

A Pull Request (PR) is a dedicated forum for discussing proposed changes to a repository before they are integrated into the main codebase.

  • Purpose: To notify team members that you have completed a feature or fixed a bug.
  • Why they exist: They provide a safety net for code review, automated testing, and discussion.
  • Real-world workflow: No one pushes directly to main. Developers branch off, do work, and open a PR to merge back safely.
💡

Why is it called a "Pull Request"?

Many beginners wonder why it's not called a Push Request since you are pushing code to GitHub.

1. You create code and push it to your own branch.
↓
2. You request the project maintainer to PULL your changes into the main branch.

"Hey maintainer, I've pushed my code. Here is a request for you to pull it into the official project."

✅ Best Practices

  • ✅
    Keep PRs Small: Easier and faster to review.
  • ✅
    Clear Titles: "Fix login bug" instead of "Update code".
  • ✅
    Detailed Description: Explain *what* changed and *why*.
  • ✅
    One Feature Per PR: Don't mix UI changes with database refactoring.
  • ✅
    Test Before Opening: Ensure your code actually runs locally.

❌ Common Mistakes

  • ❌
    Huge PRs: 50+ changed files are a reviewer's nightmare.
  • ❌
    Merging Without Review: Defeats the entire purpose of a PR.
  • ❌
    Vague Titles: Avoid titles like "stuff", "updates", or "fixed it".

    Out of Sync: Forgetting to pull latest `main` before opening PR.
Productivity Hacks

Git Aliases

Speed up your workflow with short, memorable shortcuts for the commands you use most.

What is a Git Alias?

An alias is a user-defined shortcut that expands to a longer Git command (or series of commands). It lives in your global ~/.gitconfig and is invoked exactly like any native Git sub-command.

Why do they exist?

Because you spend a lot of time typing the same long commands. An alias removes friction, reduces mental overhead and makes your workflow feel instant.

Benefits of using aliases

  • 🚀 Faster command entry
  • 🔁 Consistency across machines (when shared via dotfiles)
  • 📚 Self-documenting shortcuts (e.g. git cm = “commit-message”)
  • ⚡️ Less typing → fewer typos

Alias syntax

git config --global alias.<newAlias> "<command>"

git config – Git's configuration tool
--global – store it for the whole user
alias.<newAlias> – the shortcut name
"<command>" – the full command to run

Common mistakes

  • ❌ Forgetting quotes around commands that contain spaces.
  • ❌ Over-aliasing – turning every command into an alias makes the cheat-sheet unreadable.
  • ❌ Using aliases that clash with existing Git sub-commands.

Best practices

  • ✅ Keep aliases short (< 3 characters) and memorable.
  • ✅ Prefix with a unique character when in doubt (e.g. gco for checkout).
  • ✅ Document them in your README or dotfiles.
  • ✅ Group related aliases in a single `gitconfig` section.
  • ✅ Test each alias after creation.

Professional workflow with aliases

  1. 🔧 Setup – run the "Define a few common aliases" block once per machine.
  2. 💡 Daily work – use git cm, git st, git br throughout the day.
  3. 🚦 Review – run git lg (log graph) before merging.
  4. 🧹 Cleanup – git unstage or git reset via alias.

Comparison

git clean

  • Works on: Untracked files
  • Action: Deletes files
  • Recoverable: ⚠️ Not easily
  • Flags: -n preview, -f force

⚠️ Common Mistakes

Thinking git clean deletes tracked files

It never touches tracked files, only untracked ones.

Thinking git clean deletes modified tracked files

Modified tracked files are always safe.

Thinking git clean -n deletes anything

-n is preview-only, zero files removed.

Thinking git restore --staged removes your changes

It only unstages; your edits stay in the Working Directory.

Thinking git restore --staged restores the last commit

It does not touch file content at all, only the staging state.

Rewriting History

Resetting The HEAD

Move HEAD backwards in time. Understand exactly which layers Git touches — and when that becomes dangerous.

Why Would You Ever Want to Move Backwards?

✍️ Wrong commit message

You committed with a typo or unclear message and want to redo it.

🧩 Too many small commits

You made 5 tiny commits and want to squash them into one clean commit before pushing.

🔬 Experimental work

You tried something locally and want to cleanly undo all of it.

📦 Wrong files staged

You committed files that shouldn't be there and need to restart.

🔁 Prepare for rebase

You need to clean up local history before merging into main.

🧹 Start a feature over

You've realized the approach is wrong and want a clean slate from a known good commit.

“In all of these cases, the solution is the same: move HEAD to a previous commit. What changes is how much Git resets alongside HEAD.”

HEAD Is Not a Commit — It’s a Pointer

HEAD is simply a label that tracks which commit you are currently at. When you reset, you move this label.

↑
HEAD
After git reset <commit-B>, HEAD now points to B. Commits C and D are no longer in your active history — but what happens to their changes depends on the reset mode.
💾 Repository

The .git folder. Stores every commit and the full history.

→
📋 Staging Area

Files you have git added, ready for the next commit.

→
📁 Working Directory

Your actual files on disk. Where you write and edit code.

git reset always moves HEAD in the Repository. The reset mode decides what happens to Staging and Working Directory.

Reading History Before You Reset

git log output 
commit f7a3d91
Author: Alex Dev <alex@example.com>
Date:   Mon Jul 7 10:22:00 2026

    Add login page UI

commit b2c8e14
Author: Alex Dev <alex@example.com>
Date:   Sun Jul 6 18:45:00 2026

    Fix navbar overflow bug
  • 🔑SHA — The unique ID of every commit. You need this for git reset <commit>.
  • ✍️Message — What was changed. Helps you identify the target commit.
  • 👤Author — Who made the commit.
  • 📅Date — When it was committed. Useful for time-based orientation.
💡 Copy the first 7 characters of the SHA — that’s all Git needs for reset.

Reset Always Moves HEAD — The Mode Controls Everything Else

--soft → Moves HEAD only
--mixed → Moves HEAD + clears Staging Area
--hard → Moves HEAD + clears Staging Area + clears Working Directory
--soft

Soft Reset

✓Repository — HEAD moves to target commit
✓Staging Area — Previous commit’s changes appear here (staged, ready to commit again)
✕Working Directory — Completely untouched

💾 Repository A → B → C → D (HEAD→D)
📋 Staging Area (empty)
📁 Working Directory (clean)
→
After
💾 Repository A → B (HEAD→B)
📋 Staging Area (empty)
📁 Working Directory (unchanged)
“You made 3 small commits but want to combine them into one. Soft reset to the commit before your first small commit. All changes land in Staging — commit once with a single clean message.”

✓Repository — HEAD moves to target commit
✓Staging Area — Cleared. Changes become unstaged modified files.

Mixed reset is git reset with no flag. It clears the staging area but keeps your work in the Working Directory — you decide what to re-stage.

Why Normal Push Fails After Reset — and What Force Push Does

Local:
A→B (HEAD)
Remote:
A→B→C→D (origin/main)

After a reset, your local history is behind the remote. Git refuses to push because it would delete remote commits — it protects you.

$ git push origin main
! [rejected]        main -> main (non-fast-forward)
error: failed to push some refs to 'origin'
hint: Updates were rejected because the tip of your current branch is behind

Force Push — Overriding the Protection

$ git push origin main --force

Force push tells Git: ‘I know what I’m doing — overwrite remote history with my local history.’

Local:
A→B (HEAD)
Remote:
A→B (overwritten — C and D gone from GitHub)

⚠️ Force Push is Dangerous on Shared Branches

1 🧑‍💻 Developer A and Developer B both pull from main. Timeline: A → B → C → D
2 🔄 Developer B makes a new commit E. Timeline: A → B → C → D → E
3 ⚡ Developer A does git reset --hard B then git push --force. GitHub now shows: A → B
4 😱 Developer B tries to push commit E. Git rejects — their history no longer matches remote.
5 💥 Developer B’s entire history is now “orphaned” — they must manually resolve the conflict or lose their work.

✓ Safe Alternatives

✓git revert <commit> — Safely undoes a commit by creating a new commit. History is never rewritten. Safe for shared branches.
✓Only use --force on personal feature branches that no one else has pulled.

Soft vs Mixed vs Hard — At a Glance

Mode Moves HEAD Clears Staging Clears Working Dir Work Lost? Common Use Case Danger Level
--soft ✓ ✕ ✕ Never Squash commits, rewrite last commit message 🟩 Safe
--mixed ✓ ✓ ✕ Never Unstage wrong files, reorganize staged changes 🟡 Low Risk
--hard ✓ ✓ ✓ Yes (uncommitted) Discard all local experimentation 🔴 Dangerous

Real-World Scenarios — When to Use Each Mode

--soft

Wrong commit message

🔴 Problem: “Committed with message ‘asdf’. Embarrassing.”
💡 Solution: git reset --soft HEAD~1 → edit message → commit again
🟩 Risk: Zero — nothing is lost
--mixed

Undo a mistaken git add

🔴 Problem: “Staged the wrong files before committing.”
💡 Solution: git reset --mixed HEAD clears staging; files remain modified
🟡 Risk: Low — all code stays in Working Directory
--hard

Discard a failed experiment

🔴 Problem: “Spent 2 hours on an approach. It’s wrong. Start over.”
💡 Solution: git reset --hard <last-good-commit> — project reverts completely
🔴 Risk: Irreversible if you had uncommitted work
--soft + --force

Squash before merging

🔴 Problem: “Made 6 small commits on a feature branch. Want 1 clean commit for the PR.”
💡 Solution: git reset --soft <commit-before-feature> → single commit → git push --force (safe on personal branch)
🟡 Risk: Low — only on personal feature branch

⚠️ Common Misconceptions

⚠

“HEAD is a commit”

HEAD is a pointer that points to a commit. They are not the same thing.

⚠

“Hard reset deletes Git history forever”

Hard reset moves HEAD. Commits still exist via git reflog for ~90 days. What’s lost is uncommitted work.

⚠

“Reset automatically updates GitHub”

Reset only changes your local repository. GitHub is unaffected until you push (with --force).

⚠

“Force push is always dangerous”

Force push is safe on private feature branches no one else has pulled. It is dangerous on shared branches like main.

⚠

“Mixed reset = losing my code”

Mixed reset never touches the Working Directory. All your code is safe — it just moves out of staging.

⚠

“git restore and git reset do the same thing”

git restore --staged unstages a file. git reset moves HEAD. Completely different operations.

File Tracking Control

Git Ignore

Tell Git which files should never become part of your history — and understand exactly why that matters.

📁 Working Directory → Untracked File → git add → Tracked File → git commit → Repository

Git Ignore only influences files that have never been tracked. Once tracked, .gitignore has no effect.

Why Does .gitignore Exist?

🔐

Secret Files (.env)

API keys, database passwords, and tokens should never be committed to Git history.

📦

Downloaded Dependencies (node_modules/)

Hundreds of megabytes of packages that can be reinstalled with npm install.

🏗️

Build Artifacts (dist/, build/)

Generated output files — they change every build and bloat your history.

📋

Log Files (*.log)

Runtime logs are machine-generated noise that adds nothing to your project history.

💻

IDE Config (.vscode/, .idea/)

Personal editor preferences that vary per developer and should not be shared.

🗂️

OS Files (.DS_Store, Thumbs.db)

Invisible files created by macOS and Windows that have nothing to do with your code.

🧪

Test Coverage Reports

Generated test output — reproducible on any machine, no need to track it.

⚡

Cache Folders (.cache/, .next/)

Temporary performance artifacts that are rebuilt automatically.

Tracked vs Untracked — The Foundation

Git only knows about files you have explicitly introduced via git add. A file in your folder that has never been git added is Untracked — invisible to Git's tracking system.

📁 my-project/
├── 📄 app.js✅ Tracked
├── 📄 style.css✅ Tracked
├── 📄 README.md✅ Tracked
├── 📄 notes.txt⚪ Untracked
├── 📄 .env⚪ Untracked
└── 📁 node_modules/⚪ Untracked
Key insight: .gitignore rules only prevent Git from tracking Untracked files. If a file is already Tracked, adding it to .gitignore does nothing.
  • 📄 It is a plain text file named .gitignore
  • 📍 Placed in the root of your repository
  • 📝 Each line is a pattern telling Git what to ignore
  • 🚫 It does NOT delete files
  • 🙈 It does NOT hide files from your OS
  • ⚙️ It ONLY affects Git's file tracking decisions

# Dependencies
node_modules/

# Environment secrets
.env
.env.local

# Build output
dist/
build/

# Logs
*.log

# OS files
.DS_Store

# Editor config

Pattern Syntax — How Rules Work

Rule: password.txt

Ignores exactly one file with that exact name.

app.js
password.txt Ignored
style.css

Rule: *.log

* means "any filename". This ignores every file ending in .log regardless of name.

app.js
error.log Ignored
access.log Ignored
debug.log Ignored

Rule: node_modules/

The trailing / means "this is a folder". Every file inside it — no matter how deeply nested — is ignored.

src/
📁 node_modules/ Ignored Folder
react/
lodash/
* → matches any sequence of characters
example: *.log
✓ error.log ✓ app.log ✓ x.log ✗ app.js
? → matches exactly one character
example: file?.txt
✓ file1.txt ✓ fileA.txt ✗ file10.txt
[abc] → matches one character from the set
example: file[123].txt
✓ file1.txt ✓ file2.txt ✓ file3.txt ✗ file4.txt

Rules: *.md then !README.md

The ! prefix un-ignores a previously ignored file. Rules are processed top-to-bottom. The last matching rule wins.

README.md
matched *.md → ignored matched !README.md → un-ignored
✅ Tracked
Notes.md
matched *.md → ignored no exception
🚫 Ignored
Guide.md
matched *.md → ignored no exception
🚫 Ignored

⚠️ .gitignore Only Works For Untracked Files

Step 1 — Setup

# config.json gets committed
git add config.json
git commit -m "add config"
config.json ✅ Tracked

Step 2 — Added to .gitignore

# .gitignore
config.json
config.json ✅ Tracked Ignored?

Step 3 — The Answer

config.json ✅ Still Tracked
Git says: "I already know about config.json. It's in my tracking system. .gitignore cannot reach files I'm already tracking."

Why: Git's tracking state is stored in the index. Once a file is indexed, .gitignore patterns are never evaluated for it.

How to fix it:

git rm --cached config.json
# Now Git forgets it ever tracked this file
# .gitignore can now apply
git commit -m "stop tracking config.json"
config.json ✅ Ignored
The local file still exists on your disk — git rm --cached only removes it from Git's index, not from your file system.

🔴 Security Warning: The .env Trap

👨‍💻 1. Developer creates project — writes API keys and DB password into .env
😰 2. Accidentally runs git add .env then git commit
🌐 3. Pushes to GitHub — .env is now public in Git history
💡 4. Realizes the mistake — adds .env to .gitignore
❓ 5. "Is the secret safe now?"
❌ NO. The secret is NOT safe. Git history is permanent. Every previous commit still contains .env. Anyone with access to the repository can run: git log --all -- .env git show <commit-hash>:.env ...and retrieve the original secrets.

What you must do:

🔄
Rotate Immediately

Revoke and regenerate ALL exposed credentials right now

🗑️
Remove from index

git rm --cached .env + commit

📝
Add to .gitignore

Prevent future accidents

📚
Rewrite History (Adv)

git filter-branch or BFG Repo Cleaner

Key insight: git rm --cached removes the file from future commits — but it cannot erase it from past commits. The secret already exists in your commit history. Treat exposed credentials as permanently compromised.

Common Mistakes

❌ Myth: "I added .env to .gitignore — it's safe"
✅ Reality: Only safe if .env was never committed. Check your history.
❌ Myth: ".gitignore deletes the file"
✅ Reality: It only affects tracking. Your local file is untouched.
❌ Myth: "Adding a tracked file to .gitignore ignores it"
✅ Reality: No. Use git rm --cached first.
❌ Myth: "I can use .gitignore to hide files from collaborators"
✅ Reality: It only affects untracked files. Already-tracked files are still visible to everyone.
❌ Myth: "node_modules/ and dist/ don't need ignoring"
✅ Reality: Always ignore them — they create enormous repositories and break git clone.
❌ Myth: "I need to add .gitignore after finishing the project"
✅ Reality: Add it before your first commit. Retrofitting is much harder.
